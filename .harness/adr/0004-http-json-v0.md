# ADR 0004 - v0 全部走 HTTP/JSON，gRPC 后置

- 状态：accepted
- 日期：2026-01-01
- 决策者：服务端负责人

## 背景

内部服务之间通常用 gRPC：强类型、双向流、性能好。但 v0 的现实是：

- 单进程，服务之间是函数调用，根本没有网络序列化开销可言。
- 外部消费者（UE5 DS、Nakama 插件、运营工具、curl 调试）几乎都更愿意用 JSON。
- protoc/buf 工具链会让本地环境多一层依赖（本机实测 protoc 有、buf 无，生成插件还要额外装）。

## 决策

- v0 所有接口都是 **HTTP/JSON**，契约以 Go 声明为唯一来源，自动生成 **OpenAPI 3.1**。
- 不手写 OpenAPI，不手写 proto。契约漂移由 `apigen -check` 拦住。
- gRPC 作为"拆分服务时的可选优化"，不做预埋；切换成本 = 用同一份 DTO 生成 proto。

## 备选方案与放弃原因

| 方案 | 优点 | 放弃原因 |
|---|---|---|
| 一开始就用 gRPC + buf | 强类型、流式、代码生成 | 工具链重；DS/运营工具要额外客户端；v0 单进程收益为零 |
| 手写 OpenAPI + 手写 handler | 合约先行，语言无关 | 双份维护，必然漂移；漂移不会有人发现 |
| GraphQL | 客户端灵活取数 | 对"少量固定接口 + 强审计"的领域服务是过度设计 |

## 后果

正面：

- `curl` 就能调试全部接口；UE5 侧用现成 HTTP 客户端。
- 契约、路由、文档同源：`api.Op` 一个声明同时决定 mux pattern 与 OpenAPI。
- 零第三方依赖，CI 不需要 protoc 插件。

负面：

- **没有流式 RPC**：将来匹配进度推送、实时队伍事件要么用轮询（v0 就是轮询 `get_ticket`），要么另开 WebSocket/SSE 通道。
- **JSON 体积与解析成本**：单进程下无所谓，跨机高 QPS 时 gRPC 更省。
- **没有跨语言强类型客户端**：TS/C++ 客户端要从 OpenAPI 生成，质量取决于生成器。
- **错误类型靠字符串 code**：编译期无法校验（proto 的 enum 可以）。

## 触发重新评估的条件

- 服务真正拆到多机，且内部调用 QPS 或延迟成为瓶颈。
- 需要服务间流式通信（匹配状态推送、观战数据流）。
- 接入方超过 3 个语言栈，维护 JSON 客户端开始出错。
