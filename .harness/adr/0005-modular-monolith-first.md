# ADR 0005 - 先做模块化单体，再按需拆服务

- 状态：accepted
- 日期：2026-01-01
- 决策者：服务端负责人

## 背景

"Go 微服务"很容易变成"七个仓库、七套 CI、七份部署、七个 Dockerfile"，而团队只有几个人。
在还没有真实流量的阶段，微服务的收益（独立扩缩容、故障隔离、团队自治）几乎为零，
成本（分布式调试、网络失败、链路追踪、契约版本管理）立刻要付。

## 决策

- v0 是**一个进程、一个二进制、一个模块**（`cmd/platform`），七个服务是七个**包**。
- 每个服务保留拆分所需的全部边界：
  - 独立包 `services/<域>`，只依赖 `pkg/*`；
  - 自己的 `Store` 接口（SQL 落点）；
  - 自己的 `api.Op` 声明（路由与文档同源）；
  - 自己的 `Register(router)`（拆出去就是换一个 router）。
- 跨服务协作只允许两种方式：
  - 进程内领域方法调用（`platform/sink.go` 里的 fan-out）；
  - 或者 HTTP 调用。**不允许**跨包直接读别人的 store。
- `cmd/rank` 是拆分示例：单独跑一个服务，只比平台版多一行 `Register` 少六行。

## 备选方案与放弃原因

| 方案 | 优点 | 放弃原因 |
|---|---|---|
| 一开始就拆七个服务 | 边界清晰、真独立 | 七套部署/CI/调试；迭代速度降到十分之一 |
| 纯单体（无内部边界） | 最快 | 后期拆分要做"绞杀者"重构；现在就把边界画好几乎零成本 |
| 服务网格 + sidecar | 治理能力 | 运维复杂度远超小团队承受范围 |

## 后果

正面：

- 一条命令起全套，一条命令跑测试，改动立即端到端验证。
- 拆分是机械操作：给服务加 `cmd/<域>/main.go`，换成独立部署，接口签名不变。
- 没有分布式事务问题（v0 的扇出是进程内调用，失败可整体重试）。

负面：

- **一个进程挂全挂**：没有故障隔离。等有真实流量再拆。
- **一处分片影响全局**：内存 store 的锁在单进程下会互相影响（当前都是独立的锁，问题不大）。
- **只能水平扩副本，不能按服务扩**：匹配热点与排行热点会互相争资源。
- `platform.New` 的装配会随服务增长变得很长（那是好事，逼你正视依赖）。

## 触发重新评估的条件

- 某个服务的资源画像明显不同（CPU 密集 vs IO 密集）→ 单独拆。
- 单进程无法再用一个副本承载（QPS/内存达到单机上限）→ 按热点拆。
- 团队超过 6 人，开始按服务分小组 → 拆，让小组自治。
- 某服务的发布节奏与其它服务冲突频繁 → 拆。
