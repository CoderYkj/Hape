# ADR 0001 - Nakama 负责社交与鉴权，领域逻辑放在 Go 服务里

- 状态：accepted
- 日期：2026-01-01
- 决策者：服务端负责人

## 背景

Nakama 开箱即用：多平台登录、好友、公会、聊天、直连匹配、云存档、排行榜、钱包。
它也有 Go 运行时插件，理论上能把全部业务写进 Nakama。

团队只有几个人，没人有时间维护一套自研社交系统。但经济与进度这类逻辑一旦写进
Nakama 运行时插件，会遇到：插件跑在本进程内、改一行要重编译重启整个 Nakama、
测试只能整机起、无法独立扩缩容、账本与幂等语义要自己实现但没地方放。

## 决策

- **Nakama 保留**：登录鉴权（device/Steam/Apple）、好友、公会、聊天、云存档入口、直连匹配（社交类）。
- **领域逻辑外移**：账号映射、队伍、匹配、会话、进度、经济、排行放在独立 Go 服务。
- 边界落在 `nakama/modules/main.go`：Nakama 只做两件事——鉴权后把外部身份交给 `POST /v1/account/sessions`；转发少量 RPC 到后端。
- Nakama 的 storage 不作为钱与进度的权威来源。

## 备选方案与放弃原因

| 方案 | 优点 | 放弃原因 |
|---|---|---|
| 全部业务写进 Nakama 插件 | 一套进程、一套部署 | 无法独立测试/扩缩容；每次改动重启全部；经济审计与幂等无合适落点 |
| 完全自研账号 + 社交 | 完全可控 | 小团队重复造多平台登录、公会、聊天，成本远超收益 |
| 用 PlayFab / Firebase 替代 Nakama | 托管省事 | 厂商锁定、成本随 DAU 上升、战斗服分配仍要自己做 |

## 后果

正面：

- 领域服务可以用 `go test` 直接测，e2e 一条命令跑完整闭环。
- 经济/进度逻辑在可审计的 Go 代码里，账本、幂等、状态机都能上测试。
- Nakama 升级与领域代码解耦。

负面：

- **两个身份源**：Nakama user id 与后端 `player_id` 必须映射（`Player.ExternalID`），登录链路多一跳。
- **两个进程**：本地要同时起 Nakama 与后端才能测社交相关功能。
- 开发者要同时懂 Nakama 运行时与 Go 服务。

## 触发重新评估的条件

- 社交功能需求增长到需要专区维护（此时把社交也外移）。
- Nakama 版本升级导致插件 ABI 频繁断裂（改为纯 API 调用 Nakama，不再用插件）。
- 团队规模超过 8 人，跨进程调试成本开始低于独立部署收益。
