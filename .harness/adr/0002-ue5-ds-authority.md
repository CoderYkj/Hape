# ADR 0002 - UE5 Dedicated Server 是局内唯一权威

- 状态：accepted
- 日期：2026-01-01
- 决策者：服务端负责人 + 客户端负责人

## 背景

战斗逻辑必须在服务端跑：客户端权威会被内存修改器、抓包改包、丢包回滚直接攻破。
UE5 的 Dedicated Server 是唯一能跑同一套战斗代码、且不把战斗逻辑重写成两遍的选择。

问题不是"要不要 DS"，而是**DS 与后端的分界线在哪**，以及**信任如何建立**。

## 决策

- **局内**（命中、伤害、死亡、胜负、掉落）：只有 DS 说了算。客户端只上传输入。
- **局外**（账号、队伍、匹配、会话生命周期、进度、经济、排行）：只有后端说了算。DS 不直接写钱。
- DS 与后端的唯一接口是 HTTP + service token：
  - 进：`POST /v1/session/sessions/{id}/ready`（我起来了，地址是…）
  - 出：`POST /v1/session/sessions/{id}/results`（这是权威战报）
  - 读：`GET /v1/session/sessions/{id}`（这个 session 是不是我的、玩家是谁）
- 战报的 idempotency key 由 **DS 侧生成并持久化**（`result_id`），后端起幂等去重作用。

## 备选方案与放弃原因

| 方案 | 优点 | 放弃原因 |
|---|---|---|
| 纯 P2P / 客户端权威 | 零服务器成本 | 无法防作弊，经济系统会被立刻攻破 |
| 后端跑战斗（服务器权威模拟） | 无 DS、纯逻辑服 | UE 战斗代码无法复用；帧同步/状态同步要重写；成本更高 |
| DS 直接写数据库 | 少一跳 | 经济规则散落两处；无审计、无幂等、无账本；改规则要重新发 DS 镜像 |

## 后果

正面：

- 作弊面收敛到"DS 能做什么"，而不是"客户端能做什么"。
- DS 无状态：挂了就换一台，不丢局外数据。
- 战报链路有明确幂等点，可重放、可审计。

负面：

- **网络多一跳**：DS 必须能访问后端（内网或公网 + token）。托管环境下要配 egress。
- **DS 崩溃 = 战报丢失**：需要"僵尸 session 对账"（未实现，见 90 文档待定项）。
- **没有 relay**：客户端直连 DS，NAT/防火墙问题在一部分玩家身上会变成"连不上"，需要后续 TURN/relay 方案。
- 当前 DS 认证是共享 service token，泄露面大（有 per-allocation token 的计划）。

## 触发重新评估的条件

- 出现规模化作弊（战报被伪造）→ 立刻引入 per-allocation token + mTLS。
- 玩家"连不上"的工单占比升高 → 引入 relay 或区域化匹配。
- DS 侧战斗代码开始需要读局外状态（如背包）→ 需要设计只读快照接口，而不是让 DS 直连数据库。
