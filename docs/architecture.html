gamebackend 架构图（带标注）

一局联机对局的完整链路：证书/身份、匹配、分配战斗服、局内权威、结算扇出、回收计费。 每个方框都标了它主要做什么和验证到了什么程度。 事实来源是代码，本页与之不一致时以代码为准。生成于 2026-11-01（对应 spec 0016 的实现状态）。

✅ 已验证 CI 真跑或真机实跑，可复现 🟡 已实现未验证 代码与测试在，缺真实环境或未接线 ⬜ 未实现 有设计/契约，没有代码

1. 部署拓扑

实线 = 主要数据流；虚线 = 控制/观测流。①–⑥ 与下表的编号一一对应。

2. 每个环节主要做什么

编号环节主要功能（做什么 / 不做什么）状态代码与规格
①Nakama 登录Nakama 是身份的唯一来源：设备/第三方账号登录、发 session token。它不决定游戏内经济、不分配战斗服。✅nakama/runtime/login.lua · spec 0009
②RPC 桥接Nakama 用服务凭证调后端 account.login，把外部身份换成后端 player_id + 后端 token。客户端拿不到服务凭证，也不能自报身份。✅services/account · ADR 0010 / spec 0011
③业务 HTTP后端 token 之上的一切：读档案、排队、轮询票据、按 match 找服务器、读结算。入口按 op 声明鉴权级别（玩家 / 服务），越权与越 scope 都拒绝。✅pkg/httpx · spec 0016
④匹配与分配matchmaking 按队列与 MMR 组局；session 服务调 Allocator 申请实例，把 RUNTIME_TOKEN 与参战名单注入容器。分配失败会落 failed，不留僵尸会话。✅（Edgegap 真机）pkg/battlealloc · spec 0007/0013
⑤战斗服上报DS 先报 ready（它才知道自己监听在哪），打完报权威战报。两个报都要双凭证：服务 token（进程）+ 每场 X-Session-Token（会话）。result_id 幂等，重启复用。✅services/session · spec 0008/0012
⑥客户端直连 DSv0 无 relay：客户端拿 address:port 直接开 UDP。局内命中/伤害/胜负全由 DS 决定，客户端只送输入。✅（参考 DS 5/5 回声）ADR 0002 · spec 0013
—结算扇出战报被接受后一个事务写：战报存档 + 经验 + 钱包账本 + 评分 + 会话 finished。全成功才算结算；失败返回 503，用同一 result_id 重试，各下游幂等去重（见第 3 节图）。✅platform/sink.go · ADR 0007
—回收与对账对局结束/超时回收实例：发停止请求后回读 running=false 才算释放；没确认的进 release_pending，reconciler 每轮重试并出指标，避免"以为停了还在计费"。✅（真机 ~2s）spec 0015
—PostgreSQL14 张表的唯一持久层；每个领域两套实现（内存 / SQL），由等价性测试对齐。迁移 append-only + checksum 防篡改。✅db/ · spec 0002/0005
—Prometheus抓 /metrics：请求计数、回收积压、scope 拒绝。告警规则 1 条已写（回收卡住 15 分钟），其余 4 条仍在文档里。🟡deploy/prometheus/ · rule 95

3. 结算扇出（钱的那条路）

扇出全部成功才把会话置 finished；任何一步失败 → 503，调用方用同一个 result_id 重试，每个下游按幂等键去重。

4. 一局对局的 10 步

#动作谁做关键约束状态
1设备登录换 Nakama session客户端身份只来自 Nakama✅
2RPC login 换后端 player_id + tokenNakama → 后端服务凭证调 account.login（scope: account）✅
3入队 → worker pop → session.create客户端 / 后端一个 match 只允许一场会话✅
4申请实例并注入 env后端 → 厂商先有 RUNTIME_TOKEN 才能申请✅
5DS 报 ready（带真实监听地址）DS双凭证；重复 ready 幂等✅
6票据 → match_id → by-match 拿地址客户端只有名单内玩家可读，且不含凭证✅
7UDP 握手（参考 DS 回声）客户端 ↔ DS双向证据：发 N 收 N✅
8上报权威战报DSresult_id 先落盘再上报；409=另一份结果✅
9单事务扇出 → 会话 finished后端全成功才提交，失败可用同 id 重试✅
10释放实例 + 回读确认后端 → 厂商未确认 → release_pending + 重试 + 指标✅

5. 代码结构与"每个包负责什么"

  • cmd/platform — 单进程入口：读环境 → 装配 → 起 HTTP。✅
    • platform/ — 装配层：把 7 个服务挂到同一路由；结算扇出（sink）与 reconciler（超时清扫 + 回收重试 + 指标）也在这里。 它不实现业务规则，只负责接线与跨域事务。 ✅
    • services/*（7 个） — 每个领域一个包：DTO + Store 接口 + 内存实现 + Postgres 实现 + 路由注册 + 单测。
      • account — 玩家档案与身份兑换 ✅
      • team — 队伍与成员（一人一队、单 owner）✅
      • matchmaking — 票据、MMR 快照、pop 组局 ✅
      • session — 会话状态机、分配、双凭证、战报入口 ✅
      • progress — 经验与等级（幂等流水）✅
      • economy — 钱包与账本（余额不足、幂等入账）✅
      • rank — 评分、MMR 事件、排行榜 ✅
    • pkg/ — 基础设施，不含业务：
      • api — 接口契约声明（Op/Shape）→ 生成 OpenAPI ✅
      • apierr — 唯一错误模型（code ↔ HTTP 状态）✅
      • httpx — 路由、鉴权（玩家/服务凭证 + scope）、指标、健康检查 ✅
      • battlealloc — 分配抽象：local / edgegap ✅，gamelift / agones ⬜
      • config / logx / pg — 环境配置、结构化日志、驱动 ✅
    • ds/ — 参考 Dedicated Server（Go，不是 UE5 构建）：环境契约 + 幂等结算的可执行版本 ✅
    • clients/minimal — 客户端协议模型，CLIENT_FULL=1 会真连战斗服 ✅
    • db/ — 迁移（append-only）+ 约束断言 ✅
    • deploy/ — dev/prod compose、systemd 单元、prometheus 规则 🟡 未上真机
    • .harness/ — 规则、规格、ADR：这个仓库的"决策记录" ✅

契约链路：api.Op 反射 → tools/apigen → api/openapi/*.json → CI 用 apigen -check 拦住"改了代码没重新生成"。

7. 安全与凭证

玩家身份 ✅

  • Nakama 发会话，后端签发自己的玩家 token（iss=gamebackend）
  • 登录口只对服务开放，客户端不能自报身份（ADR 0010）

DS 双凭证 ✅

  • 服务 token = 进程身份
  • X-Session-Token = 这一场的身份
  • 缺一个 401；只写长度不写值进日志

轮换 ✅

  • 多凭证并行，日志 caller= 指认调用方
  • 四步零停机：加 → 验 → 迁 → 删

最小权限 ✅

  • name=token:account：只能调声明的服务
  • 越权 403（不是 401）；默认拒绝；拼错 scope 启动失败
  • 观察模式 + 计数判据，再切强制

mTLS / 短期凭证 ⬜

  • scope 解决"能做什么"，不解决"凭证长期有效"

UE5 引擎侧 ⬜

  • DS 与客户端在引擎里都未构建；协议已由 ds/ 与 clients/minimal 钉住
