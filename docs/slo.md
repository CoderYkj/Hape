# SLO 草案 v0（待业务确认）

- 状态：**草案**。可以照着测，但目标值需要产品/制作人拍板（见 §5）。
- 依据：spec 0019 的本机压测基线、现有 8 条告警指标、当前部署形态（**单机、无 HA**）。
- 一句话：这份文件先回答"**我们打算承诺什么、怎么量、算不算得出来**"，
  数字本身是可改的——不可改的是"承诺必须有测量支撑"。

## 0. 建议的 6 个 SLI / SLO

| # | SLI | 建议目标（v0） | 窗口 | 现在能测吗 |
|---|---|---|---|---|
| 1 | API 成功率 = 非 5xx / 全部契约 op | **≥ 99.5%**（单机形态；见 §4 的 99.9% 前提） | 30 天 | ✅ `backend_requests_total` |
| 2 | 结算延迟 `session.submit_result` p99 | **≤ 300ms** | 30 天 | ✅ 新加直方图 `backend_request_duration_seconds` |
| 3 | 分配发起延迟 `session.create` p99（**不含厂商等待**） | **≤ 800ms** | 30 天 | ✅ 同上 |
| 4 | 分配成功率（进入 allocating 且未失败） | **≥ 99.5%** | 30 天 | ⚠️ 需新增 counter（现在只能从 sessions 表反推） |
| 5 | 回收确认及时率 = `unreleased_allocations > 0` 的时间占比 | **≤ 0.1%** | 30 天 | ✅ `backend_unreleased_allocations` |
| 6 | 一局端到端成功率（ready → finished） | **≥ 99.5%** | 30 天 | ⚠️ 需 DS 侧指标（v1 契约里没有） |

排除项（必须写明，否则 SLO 是自欺）：厂商分配失败、玩家网络问题、计划内维护窗口。

## 1. 为什么是这些数字

- **基线**（本机、单进程、loopback）：内存 store 307 场/秒、total p50 80ms / p99 95ms；
  Postgres 121 场/秒、p50 59ms / p99 537ms。SLO 在基线之上留余量，不是拿基线当目标。
- **300ms 的结算 p99**：比本机 PG 的 p99（537ms，含连接池与行锁竞争）更严，但那是
  **10 并发短脉冲**下的数字；稳态下应明显更好。若实测达不到，先修尾巴（连接池/索引），
  再把目标改成可达的值——**不要反过来**。
- **99.5% 而不是 99.9%**：当前是单机 + 单 PG、没有 HA、没有多副本。99.9% 意味着每月
  只有 43 分钟不可用，而一次重启/迁移/恢复演练就不止这个数。先把 99.5% 做扎实，
  等有 HA（多副本 + PG 主备 + 反代健康检查）再提 99.9%。
- **回收确认 ≤ 0.1% 的时间**：这一项直接对应钱，所以给得比 API 更严；它衡量的是
  "存在我们说不清状态的实例"的时间占比，而不是"失败次数"。

## 2. 怎么算（PromQL，全部基于仓库里的指标）

```promql
# 1) API 成功率（30 天）
1 - (
  sum(increase(backend_requests_total{status=~"5.."}[30d]))
  /
  clamp_min(sum(increase(backend_requests_total[30d])), 1)
)

# 2) 结算 p99（5 分钟窗口滚动，长期用 recording rule 聚合）
histogram_quantile(0.99,
  sum(rate(backend_request_duration_seconds_bucket{op="session.submit_result"}[5m])) by (le))

# 3) 分配发起 p99
histogram_quantile(0.99,
  sum(rate(backend_request_duration_seconds_bucket{op="session.create"}[5m])) by (le))

# 5) 回收确认不良时间占比（近似：gauge > 0 的采样比例）
avg_over_time((backend_unreleased_allocations > bool 0)[30d:1m])
```

第 4 项与第 6 项目前**没有指标**，对应两个工作项（§6）。

## 3. 错误预算与冻结规则

| 预算消耗 | 动作 |
|---|---|
| < 50% | 正常发布 |
| ≥ 50% | 停止非必要发布；优先修可靠性问题 |
| 100% | 只做修复与可靠性；发布需要负责人签字 |

预算按月滚动，**不结转**。发布冻结不追溯（已经发布的回滚不算额外消耗）。

## 4. 容量包络（从基线推到"要几台"）

| 口径 | 数字 | 怎么用 |
|---|---|---|
| 单进程峰值（PG） | 121 场/秒 ≈ 7.3k 场/分 | 短脉冲实测；稳态容量应低于此 |
| 一局时长假设 3 分钟 | 单机理论并发 ≈ 21k 局 | **不要当真**：受 DB 连接池与单机 CPU 限制，需 soak 验证 |
| 扩容触发 | 结算 p99 连续 10 分钟超 SLO / `oldest_allocating_seconds` 持续上升 / DB 连接池饱和 / CPU > 70% 持续 10 分钟 | 任一触发即扩，不等告警连片 |

缺口：本轮只有**短脉冲**压测，没有 soak、没有多机、没有真实网络。所以 §4 的数字是
"量级参考"，不是容量承诺。

## 5. 需要业务拍板的三件事（没有这三项，SLO 定不下来）

1. **目标规模**：内测/首发的峰值并发对局是多少？（决定要不要现在就上多副本/多区域）
2. **结算时效的产品要求**：玩家打完多久看到奖励算合格？1 秒？5 秒？10 秒？
   （决定 §0 第 2 项是 300ms 还是 1s）
3. **可用性窗口**：是否接受固定维护窗口？若有，SLO 计算要不要排除该窗口？
   （决定 99.5% 的分母）

## 6. 现在缺的测量能力（工作项）

| 缺什么 | 影响哪条 SLO | 怎么补 |
|---|---|---|
| 分配失败计数 | 第 4 项 | `backend_allocations_failed_total` counter（Allocate 返回错误处 +1） |
| DS 侧指标（上报成功/失败、上报耗时） | 第 6 项 | 需要 DS 暴露指标或上报时带上结果，属契约 v2 讨论 |
| 长期存储（30 天 retention 已配 15d） | 全部月度窗口 | 提高 retention 或加远端写入 |

## 7. 与现有告警的对应关系

| 告警 | 对应 SLO | 说明 |
|---|---|---|
| `HighServerErrorRatio` | #1 | 5xx > 1% 持续 5 分钟，是 99.5% 的早期信号 |
| `SessionsStuckAllocating` | #3/#4 | 分配卡住会同时拉低延迟与成功率 |
| `DedicatedServerReleaseStuck` / `UnreleasedAllocation` | #5 | 直接对应"说不清状态的实例" |
| `ZombieSession` | #6 | 端到端没走完的可见症状 |
| `EconomyInternalError` | #1（权重更高） | 钱的 op 失败一次就值得看 |

## 8. 验证计划（证明目标可达，而不是假设）

1. **soak**：50% 目标吞吐跑 1 小时，观察 p99 漂移与内存/连接池；
2. **峰值**：3 倍目标吞吐跑 5 分钟，确认 p99 不崩、错误率不升；
3. **故障注入**：DB 断开 5 秒、厂商返回 503、DS 上报前崩溃重启——各自观察 SLO 与告警是否符合预期；
4. 每项记录到 `docs/deploy.md` 的"已验证"表，并在 spec 里留证。

## 9. 明确不做

- 不做多区域 / 多活 SLO（形态还没到）。
- 不做客户端侧 SLI（需要客户端埋点，属 UE5 客户端工作）。
- 不承诺"零停机发布"（单机形态下做不到，写了就是假承诺）。
