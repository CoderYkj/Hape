# 架构简报：给技术总监 / 制作人 / 创始人

> 用途：一次架构宣讲 + 评审，也适用于面试场景里的"讲一个你做过的系统"。
> 目标不是证明这套代码能直接扛住某个量级，而是证明三件事：
> **我能把边界划清、把风险量化、把没验证的东西自己说出来。**
>
> 配套材料（都在仓库里，可现场打开）：
> - `docs/architecture-map.html` —— 现在长什么样，每个环节做什么，逐项标注验证状态
> - `docs/roadmap.html` —— 还剩什么、被什么卡、完成判据
> - 终端演示：`go run ./cmd/platform` + `go run ./tools/fakeds`（10 秒看到一局完整对局）

---

## 0. 90 秒版本（电梯陈述）

> 我做的不是又一个后端模板，而是**一条能跑通、能复现、并且自己会承认边界的对局闭环**。
>
> 一局联机对局要走完：登录 → 匹配 → 申请战斗服 → 战斗服上报 → 结算发奖 → 回收实例。
> 这条链路上有四个地方最容易出事：**谁说了算**（权威边界）、**战报会不会重复结算**、
> **接口改了客户端不知道**、**实例停了没停**（钱）。
> 我把这四个地方各自变成了一条可执行的规则，然后给每条规则配了能跑的验证。
>
> 规模上很小：7 个域、22 个接口、14 张表、8 个 CI job。但**同一条链路上，
> 我有 4 件事情诚实地说没验证过**，每一件要多少人日关掉我都能给出来。
> 我觉得这比"什么都做完了"更值得你花 20 分钟。

**三个数字先立住**：7 域 / 22 接口 / 14 表；8 个 CI job 全绿；一局真实对局由**三个独立进程**（客户端、厂商、战斗服）跑通，包含 5/5 UDP 回声与一次结算。

## 1. 技术总监视角：九个决策，每个都带"为什么"和"证据"

顺序即重要性。每条都是"取舍"，不是"最佳实践"。

### 1.1 权威边界表（谁说了算）

| 决策 | 权威 | 客户端能否影响 |
|---|---|---|
| 局内命中、伤害、死亡、胜负 | UE5 Dedicated Server | 否（只送输入） |
| 实例是否存在、地址端口 | 托管厂商（Allocator） | 否 |
| 谁和谁匹配 | matchmaking 服务 | 只能决定自己排不排 |
| 结果如何进入经济/进度/排行 | session 服务 | 否 |
| 玩家身份 | Nakama | 提供凭据，不决定身份 |
| 余额、价格、掉落 | economy 服务 | 否 |

**为什么先讲这个**：引擎/服务协作的事故，八成不是性能问题，是"两边都以为自己说了算"。
边界表一旦写死，就能推导出下面所有实现约束——比如"战报只认 DS，且必须能证明是**这一场**的 DS"。

**证据**：`rules/90` 是这张表的规则版；`e2e` 里有一条"客户端伪造战报 → 401"的断言。

### 1.2 双凭证：进程身份 ≠ 会话身份

战报上报要同时带两个凭证：

```text
Authorization: Bearer <service token>    # 进程身份：一台可信机器
X-Session-Token: <RUNTIME_TOKEN>         # 会话身份：就是这一场的 DS
```

**为什么**：只有共享 token 时，任何被攻破的机器都能给**任意一场**对局上报战报——那等于"DS 是唯一权威"这句话没有实现。加了每场凭证后，一台被攻破的实例只能替自己那一场说话。

**证据**：缺 `X-Session-Token` → 401；拿别场的 token → 401；`session.get`（玩家读）永远不含该字段。

### 1.3 结算：一个事务 + 幂等键

战报被接受后，**一个数据库事务**里写五处：战报存档、经验、钱包账本、评分、会话完成。
全成功才提交；任何一步失败返回 503，DS 用**同一个 `result_id`** 重试，每个下游按幂等键去重。

**为什么**："钱不能重复发"和"钱不能少发"是两个方向的错，必须同时防。只做幂等不做事务 → 半成功；只做事务不做幂等 → 重试双倍。

**证据**：重放同一战报 → `applied=false`（不是错误也不是二次入账）；真库上的等价性测试断言账本只有一行。

### 1.4 契约先行 + 防漂移

接口不是写在文档里的，是**代码里声明的**（`api.Op`），由生成器产出 OpenAPI，CI 跑 `apigen -check`，改了代码不重新生成就红。

**为什么**：客户端/服务端/QA 三方对接口的成本，远高于生成一次 JSON。而且"文档漂移"这种债，利息是联调时间。

**证据**：22 个 op 全部来自生成物；契约测试还会校验"每个 service-auth op 必须能被某条凭证的 scope 覆盖"——**加接口忘了配权限，CI 就拒绝**。

### 1.5 双实现等价性测试（内存 vs SQL）

每个领域两套 store：内存（本机零依赖、测试秒级）和 Postgres（生产）。同一个测试套件跑两遍，逐步断言两者行为一致。

**为什么**：小团队最怕的是"本地好好的，上库就炸"。等价性测试把"两种实现的差异"变成 CI 里的红。

**证据**：真库上跑出的真实 bug 就是这类——`scanSession` 的列数从 15 变成 17 时，SQL 路径才报错（见 §7 战例）。

### 1.6 DS 运行时契约（把文档做成可执行）

`ds/` 是一个**参考战斗服**（Go，不是 UE5 构建）：读厂商注入的环境变量 → 监听 UDP → 报 ready → 打一局 → 上报权威战报。启动第一行只打印**长度**：

```text
ds: session=s_x runtime_token=present(len=43) service_token=present(len=11) ...
```

`result_id` 在**上报之前**落盘，崩溃重启后复用；`reported_at` 写入后重启直接退出。崩溃演练用退出码 17（刻意）与 1（真失败）区分。

**为什么受重视**：UE5 DS 接入最容易踩的坑就是"重试变成两次结算"和"凭证没注入"。我把这两条变成了可执行、可演练的契约，UE5 上线时只替换二进制，接口与变量名不变。

**证据**：CI 的 `ds` job 跑三种形态——容器里真打一局、进程形态再打一局、崩溃重启后只结算一次；还有一个"缺 `RUNTIME_TOKEN` 必须拒绝启动"的负向断言。

### 1.7 回收回读：`DELETE` 返回 200 ≠ 实例停了

停止请求被接受只是"厂商收到请求"。真正的释放是轮询状态接口直到 `running=false` 或 404；没确认的进 `release_pending`，由对账任务重试，并出指标。

**真实实测（不是文档抄的）**：分配 → READY **4s**；停止 → `running=false` **2.0s / 0.7s**（两次）；状态序列 `Status.READY → Status.TERMINATING`，而且 **`running` 先变 false，状态字符串还停在 TERMINATING** —— 所以判定必须看 `running`，等字面量 `TERMINATED` 只是多一个超时竞态。

**为什么值钱**：托管战斗服按秒计费。回收不确认就是**持续漏计费**，且只在账单上可见。这条现在有指标 + 一条 15 分钟告警。

### 1.8 凭证治理：先能换，再限权

- **轮换**：多凭证并行 + `caller=` 日志，四步零停机（加 → 验 → 迁 → 删）；旧的与新的表达式互斥，避免"以为退役了其实还在用"。
- **最小权限**：凭证声明可调哪些**服务**（`name=token:account`），越权 **403 而不是 401**（凭证是真的，只是不允许做这件事——这两种错误把 on-call 引向完全不同的地方）；默认拒绝；拼错的 scope 启动失败；先观察模式（只记 `would-deny` + 计数）再强制。

**为什么**：长期共享密钥的现实是"永远换不掉"。而 scope 保护的是**钱和配额**（`economy.grant`、`session.create`），不是积分榜——伪造战报本来就被 1.2 挡住了。

### 1.9 可观测性：把"应该关注"变成数字

- 日志固定字段：`request_id / op / op_service / caller / status / duration_ms`（`caller` 就是"谁在用哪条凭证"的唯一证据）
- 指标：请求计数、回收积压（`pending_sessions / max_attempts / oldest_pending_seconds`）、scope 拒绝（强制 与 观察两个计数器）
- 八条告警规则：回收未确认、未释放分配、分配卡住、僵尸对局、5xx 比例、结算延迟、越权调用、经济 500
- 计数器**零值也注册**——否则 `rate()` 要等"坏事发生过一次"才有数据

## 2. 制作人视角：这套东西到底省什么

不讲技术，讲"能少做多少事"。

| 它省的是 | 具体怎么省 |
|---|---|
| 接口联调返工 | 接口从代码生成，改了就红；不存在"文档上是这个、实现是那个" |
| 结算争议 | 每一笔都有账本 + 幂等键 + 战报原文，能回答"这个玩家为什么多 100 金币" |
| 上线前"能不能跑" | 一条命令起平台，一条命令模拟完整对局；不依赖引擎、不依赖厂商账号 |
| 战斗服接入的反复 | 环境变量契约 + `result_id` 幂等已经做成可执行版本，UE5 侧照着实现即可，且有演练脚本 |
| 新人上手时间 | 规则/规格/ADR 在仓库里；架构图带"验证到哪一步"的标注，新人不会误以为一切都跑通过 |

**风险怎么讲（一定要主动讲）**：我不会说"这些坑不存在"，我给的是**关闭成本**：

| 未验证项 | 前置条件 | 估算（人日，依据本仓库同类工作实际耗时） |
|---|---|---|
| Edgegap `env_vars` 在实例内可见 | 已发布镜像 + 一次分配 | 0.5 |
| 计费对账（停计费时刻） | 厂商账单/控制台权限 | 1–2 |
| Prometheus 接一台真实例 + soak 压测 | 一台能跑 Prometheus 的机器 | 1–2 |
| 生产部署（systemd/TLS/备份恢复演练） | 一台真机 | 3–5 |
| UE5 DS 二进制 | 引擎 + 许可 + 构建环境 | 1–2 周（不含引擎侧前置） |
| UE5 客户端 | 同上 + 真机可连 | 2–4 周 |
| 多实例选主 / mTLS | 决定拆分时 | 约 1 周 |

> 这些是**估算**，不是承诺。判据是"能被验证的事实"，不是"我觉得差不多"。

**30 / 60 / 90 天（如果我来带这条线）**

- **0–30 天**：把"未验证项"按上表逐个关掉；建立 CI 基线（现在的 8 个 job 加压测入口）；和生产/运维对齐一次真实部署。
- **31–60 天**：与引擎组敲定 DS 契约的两个未决点（玩家进入事件、掉线重连）；上线一版**内部可玩**的完整对局；把结算口径与审计流程写成文档并被财务/运营确认。
- **61–90 天**：压测出容量数字与瓶颈清单；决定是否拆分（拆的触发条件写进 ADR）；给出成本模型（每场对局的服务器成本 + 人力）。

## 3. 创始人视角：钱与组织

**成本结构（这个项目最特殊的一点）**

- 后端常驻成本很低（单机 compose：一个后端进程 + Postgres）。
- **真正的变动成本在战斗服**：托管厂商按秒计费，空转的实例就是纯亏损。
  所以"回收确认 + 积压告警"不是洁癖，是**直接对应账单**的功能。
- 什么时候成本模型会变：当并发对局数超过单机上限（我要先测出来），或需要多区域就近分配时，成本从"一台机器"变成"一组实例 + 编排 + 带宽"。

**风险与组织**

- 最大的风险不是技术选型，是**"最后一公里"没人做**：真机部署、UE5 两个二进制、计费对账。这三件不做完，前面所有工作都只是"看起来完整"。
- 小队杠杆：这套东西的定位是"1–2 个人能持续维护的后端骨架"。模块化单体是**刻意的**——小团队上微服务的成本（部署、观测、联调、值班）远高于收益；拆分的触发条件我写在 ADR 里，不是"以后再说"。
- 我需要什么样的队友：一个偏基础设施/运维（部署、观测、容量），一个偏游戏服务/数据（结算口径、反作弊、数据分析）。引擎侧由 UE 组负责，我只提供契约与验收判据。

## 4. 规模差距：从"一台机器"到他们的量级

**这一节必须我主动讲**，否则会被合理地怀疑"不懂规模"。

现在这套东西的硬边界（我自己标注的）：

| 维度 | 现在 | 说明 |
|---|---|---|
| 部署 | 单机 compose / systemd | 无水平扩展，进程内有状态（reconciler、内存 store） |
| 数据 | 单 Postgres、单库事务 | 结算靠单库事务保证原子性 |
| 扇出 | 进程内调用 | 没有消息队列，重试靠调用方 |
| 分配 | 1 个并发部署槽（厂商 plan 限制） | 一次只能有一台实例 |
| 可观测 | 手写指标 + 8 条规则 | 无 tracing、无日志聚合、无长时间压测 |

他们的量级需要、而这里没有的：无状态水平扩展（会话状态外置）、分区分服与就近匹配、缓存层、异步/最终一致的结算 + 对账、DS fleet 编排（Agones 或自研）、多区域、全链路 tracing、灰度与容量压测、成本核算。

**哪些可以不变，哪些必须换**（这是判断力所在）：

- **不变**：权威边界、双凭证模型、`result_id` 幂等语义、契约生成与漂移检查、DS 运行时契约、状态机。
- **必须换**：进程内 sink → 消息总线（结算从"单库事务"变成"事件 + 幂等消费 + 对账"）；内存 store → 只留测试用；单机 reconciler → 带选主的分布式任务；单实例限制 → fleet 编排。

**一句话**：架构的价值不在"现在能扛多少"，而在**哪些决策在扩容时仍然成立**。我列出来的"不变"那一栏，就是我认为能带过去的资产。

## 5. 现场演示脚本（2 分钟，不联网也能跑）

```bash
# 终端 1：起平台（内存存储，零依赖）
go run ./cmd/platform

# 终端 2：模拟一场完整对局（登录→排队→分配→ready→战报→结算→读回收益）
go run ./tools/fakeds

# 想证明"凭证真的进了战斗服实例"，而不是本进程扮演 DS：
go run ./tools/fakeds -launch-ds exec
# 输出里会有：runtime_token=present(len=43) → 只打长度，不打值

# 崩溃重启只结算一次：
go run ./tools/fakeds -launch-ds exec -crash-restart
```

演示时讲三句话：**这条链路是真的在跑**；**每个上报都有双凭证**；**我能指出它哪里没验证**。

## 6. 白板讲解法（3 分钟让人理解权威边界）

画三个框 + 两条线：

```text
[客户端] --HTTP--> [后端] --分配--> [战斗服]
    |                                  ^
    +----------UDP 直连----------------+
```

然后说三句：

1. **客户端不决定任何结果**，它只送输入；局内一切由战斗服决定。
2. **后端不参与局内**，它只决定"这台机器是不是这一场的、这份战报收不收"。
3. **战斗服只替自己那一场说话**（每场凭证），所以它被攻破也污染不了别的场次。

这三句就是整套实现的来源：如果这条线不成立，后面所有代码都是装饰。

## 7. 附录 A：追问清单（红队）与回答骨架

> 每个问题都先写"对方真正想听什么"，再给回答骨架。诚实优先：不知道就说不知道，然后给"我会怎么查"。

| 问题 | 真正想听 | 回答骨架 |
|---|---|---|
| **这套能扛多少 CCU？** | 你知不知道自己东西的边界 | 直接说：**不能扛**，并给瓶颈清单（单进程、进程内状态、单库事务扇出、无缓存、无压测数据）。然后给扩容路径与"哪些决策不变"（§4）。最忌讳给一个拍出来的数字。 |
| **为什么自研而不直接用 Nakama 全家桶 / PlayFab？** | 你是否评估过现成方案 | Nakama 留下做**身份与社交**（它的强项），域逻辑（结算/经济/排行）自己做，因为要能审计、要能改口径、要能和 DS 契约对齐。如果项目只是"能玩就行"，直接用托管更快——这是我当时的取舍，写在了 ADR 里。 |
| **UE5 DS 你写过吗？** | 是否会不懂装懂 | 引擎侧二进制我没写（如果没有，就直说）。我做的是**把它变成一个可验收的契约**：环境变量表、两个上报接口、`result_id` 幂等、崩溃重启演练。引擎同事照这个实现，我可以验收。 |
| **结算为什么不用消息队列、最终一致？** | 你是否理解一致性的取舍 | 现在单库单事务，是因为规模还没到需要拆，且"发奖"这种操作在小规模下强一致更省心。拆的触发条件、拆完怎么保幂等、怎么对账，我写在 `roadmap` 里。 |
| **怎么保证不重复发奖？** | 幂等的基本功 | 三层：DS 侧 `result_id` 先落盘后上报（重启复用）；服务端按 `result_id` 判重（重放返回 `applied=false`）；数据库幂等键唯一约束兜底。测试里有重放断言。 |
| **你遇到过最难的问题？** | 排查方法论 | 讲真实战例（见 §8），重点讲**怎么发现的**、**为什么之前没发现**、**加了什么防再犯**。 |
| **测试策略是什么？** | 会不会写出"看起来有测试"的工程 | 四类：等价性测试（内存 vs SQL，同一套断言跑两遍）、假厂商契约测试（httptest 模拟厂商 API 的每种响应）、覆盖性测试（示例配置必须能触达每个 service-auth op）、防跳过断言（CI 里断言数据库套件"没有被 skip"——skip 看起来像 pass）。 |
| **带过团队吗？怎么分工？** | 是否能当负责人 | 用 §3 的分工与 §2 的 30/60/90 回答；强调我会把"验收判据"写下来，而不是靠口头。 |
| **如果给你三个人、两个月，你做什么？** | 优先级判断 | 先关未验证项（尤其真机部署与 DS 契约），再谈新功能；两个月内目标：一局**内部可玩**的真实对局 + 容量基线数字。 |
| **你怎么看我们现在的后端？** | 会不会贬低现有系统 | 不了解内部，不评价。我会问四个问题：现在的痛点是延迟、成本、迭代速度还是稳定性？战斗服是自建 fleet 还是托管？结算口径谁定、谁审计？团队规模与我能改的边界？ |

## 8. 附录 B：三个真实战例（讲过程，不讲结论）

面试里"你遇到过什么 bug"是最能区分真做过和背过答案的一题。这三个都是真实发生并修复的：

1. **`go run` 吞掉了子进程的退出码**。崩溃演练里，战斗服故意以 17 退出，但工具报 1 —— 因为 `go run` 用自己的退出码覆盖了。现象是"演练失败"，本质是**验证工具本身不可信**。修复：先 `go build` 再直接执行，并写进注释"厂商不会用工具链启动进程"。
2. **备份是坏的，但当天没发现**。CI 里 `pg_dump` 是 17、服务端是 16，dump 里带 `SET transaction_timeout = 0`，PG16 直接报错 → 恢复失败。**备份成功、恢复失败**是最坏的组合。修复：备份端与恢复端都加版本护栏（客户端比服务端新就拒绝），并在 CI 里用同版本镜像跑脚本。
3. **SQL 路径少扫了两列**。给会话加两列后，我只改了公用的扫描函数，漏了另一条内联 `Scan`，报错是 `number of field descriptions must equal number of destinations, got 17 and 15`。**内存实现全绿，只有真库才炸** —— 这就是为什么等价性测试必须在真库上跑。

回答结构固定：**现象 → 为什么之前没发现 → 根因 → 修复 → 防再犯的机制**。最后一条最重要。

## 9. 附录 C：语言纪律（不要说的话）

| 不要说 | 改说 |
|---|---|
| "这套可以直接上生产" | "这套能跑通闭环；上生产还差 5 项，成本在下表" |
| "能扛百万 CCU" | "还没压测；瓶颈我列出来了，压测后才能给数字" |
| "我们用微服务/K8s，比较先进" | "这个规模模块化单体更省；拆分触发条件写在 ADR 里" |
| "现有系统肯定不行" | "我不了解内部，想先问四个问题" |
| "我保证 / 肯定没问题" | "判据是这个，验证方式是那个" |
| 贬低引擎组/客户端组 | "引擎侧我提供契约和验收判据，具体实现他们更专业" |

**一条总原则**：**形容词换成判据**。"高可用"→"故障时 X 秒内切换到 Y"；"高性能"→"压测给出 P99 与并发上限"。
