## 1. 三条并行主线

三件事互相**不阻塞**，可以并行推进（一条线的外部条件卡住时，另两条照走）。

### 主线 A：观测 → 容量

| 顺序 | 项 | 依赖 | 状态 |
|---|---|---|---|
| A1 | Prometheus 接上（抓 `/metrics`） | 一台能跑 Prometheus 的机器 | ✅ 配置 + profile + CI 校验（spec 0019） |
| A2 | 补齐剩下 4 条告警（5xx>1%、分配卡住、僵尸对局、经济 internal） | A1 | ✅ 8 条规则 + 所需指标（spec 0019 / 0020） |
| A3 | 压测（每场对局的 QPS/延迟/并发会话） | A1 | 🟡 工具 + 本机基线（内存 307/s、PG 121/s）；缺 soak 与多机 |
| A4 | SLO 与容量决策（要几台、什么规格） | A2 + A3 | ⬜ |

### 主线 B：引擎内（两个二进制）

| 顺序 | 项 | 依赖 | 状态 |
|---|---|---|---|
| B1 | 参考 DS（`ds/`，Go） | 无 | ✅ 容器内真打一局 |
| B2 | UE5 Dedicated Server（替换 B1 的二进制） | UE5 引擎 + 许可 | ⬜ 契约已定（spec 0012） |
| B3 | UE5 客户端（登录/排队/连 DS/结算页） | B2（要先有真机可连）+ 协议（已定） | ⬜ C++ 片段未编译 |
| B4 | 真机联调（一次完整对局，人真的在里面打） | B2 + B3 | ⬜ |

### 主线 C：平台演进

| 顺序 | 项 | 依赖 | 状态 |
|---|---|---|---|
| C1 | mTLS 或短期凭证（替代长期共享密钥） | 无 | ⬜ |
| C2 | M4 服务拆分：rank/matchmaking 独立进程 | C1 + 消息队列或 gRPC | ⬜ |
| C3 | 进程内 sink 换消息总线（结算扇出跨进程） | C2 | ⬜ |

### 1.1 执行顺序（按"最短板"排序）

排序原则：**代码已经不是最短的那块板**。决定这套东西是"脚手架"还是"系统"的，是第一次
真机部署与可量的容量基线；唯一会**阻塞引擎进度**的是 DS 契约的跨团队评审。剩下纯靠代码能
补的项（§2 前四行）都很小，插在任何空档做即可——不要为它们推迟 1 和 3。

| # | 做什么 | 为什么现在 | 判据 | 估算 |
|---|---|---|---|---|
| 1 | **第一次真机部署**：systemd / compose + TLS 反代 + 备份恢复演练 + 重启与磁盘验证 | 代码只在 CI 容器与本机跑过，**从未在一台真机上**；这是"脚手架 → 系统"的分界 | 机器重启后数据在；备份恢复到新库后服务能起；TLS 下客户端能连；`/metrics` 被采集到 | 3–5 人日 |
| 2 | ~~Prometheus + 告警 + 压测基线~~ → **已做（spec 0019）**；剩下的是接一台真实例与 soak | 规则与指标的一致性在 CI 里校验过，但**没有真实 Prometheus 采过**，也没有 1 小时以上的持续压测 | 8 条规则各被真实流量触发一次；soak 1 小时后 p99 与内存不漂 | 1–2 人日 |
| 3 | **DS 运行时契约评审**（交给 UE5 组） | 唯一会**阻塞引擎进度**的事；越早暴露"他们还缺什么"越好 | 引擎组确认 env 表 + 两个上报接口 + `result_id` 幂等可照做；6 件待拍板项有结论（`docs/ds-runtime-contract.md` §6） | 0.5 人日（一次会） |
| 4 | **计费对账 + Edgegap `env_vars` 复验** | 两者都只差"一次真实操作"，但直接对应钱 | 见 §2 判据 | 1.5–2.5 人日 |
| 5 | **三份 ADR**：战报 `schema_version` / 掉线重连的会话模型 / 结算事件化（outbox）路径 | 纯设计、成本低；等 UE5 上线或拆分时再想，就是推翻重来 | 三份 ADR 通过评审，写清触发条件与兼容策略 | 1–2 人日 |

**现在不要做**（每条都有触发条件，不是"以后再说"）：

| 不做 | 触发条件 |
|---|---|
| K8s / 服务网格 / 微服务拆分 | 单机并发对局数超基线，或多区域就近分配成为需求（M4） |
| GameLift / Agones 适配器 | 选定第二家厂商，或 Edgegap 在某区域不可用 |
| 反作弊行为分析 | 有真实玩家数据与"被刷"的实际案例 |
| 性能优化 | 先有压测基线；没有数字的优化都是猜测 |
| 多实例 reconciler 选主 | 后端要跑多副本（M4 之后） |

**分工建议**

- **1 人**：1 → 2 → 4，第 3 项（契约评审）插在任意当天——它不占工时，但可能改变后面所有事。
- **2–3 人**：A 做 1（部署与运维），B 做 2（观测与压测），负责人做 3 + 4 + 5（契约、钱、ADR）；
  第 4 项里的 `env_vars` 复验可以顺手做掉。

> 一句话：**先让它在真机上跑起来，再让数字说话。**

## 4. 明确未实现的技术项

| 类别 | 项 | 说明 |
|---|---|---|
| 引擎 | UE5 Dedicated Server | 环境契约、双凭证、`result_id` 幂等都已定；二进制未建 |
| 引擎 | UE5 客户端 | `docs/ue5-client-model.md` 的 C++ 是形状指引，未在引擎里编译 |
| 引擎 | UE5 侧 CI（引擎构建） | 需要引擎与许可，且构建很重 |
| 厂商 | GameLift / Agones 适配器 | 照 `pkg/battlealloc/edgegap.go` 的结构写，契约测试用假服务 |
| 对局 | DS 掉线重连 | 需要 DS 侧保存每局连接状态（契约 §6 第 3 项：v1 明确不承诺）；客户端"token 过期重登"已做，缺的是**对局内重连** |
| 对局 | 战报 `schema_version` | 加字段，便于以后兼容旧战报（契约 §6 第 5 项） |
| 对局 | `ready → in_progress` 无人置位 | 只有提交战报时隐式跨过（`services/session/service.go`）；契约 §6 第 1 项的 `session.mark_in_progress` 没实现，所以 `ZombieSession` 的 in_progress 分支基本不会触发 |
| 对局 | 反作弊（异常战报检测） | 现在是"谁能提交 + 提交什么"的边界，不是行为分析 |
| 平台 | 多实例 reconciler 单活选主 | 现在多实例会重复 Release（安全但费配额） |
| 平台 | 进程内 sink 换消息总线 | 结算扇出跨进程后需要（配合 M4） |
| 平台 | **生产形态缺 Nakama** | `docker-compose.prod.yml` 只有 postgres + backend；JWT 校验需要外部 Nakama，而它的生产形态（Nakama 自己的库、`BACKEND_JWT_KEY` 分发、升级路径）既没有编排也没有 runbook |
| 运维 | 生产数据库运维 | 备份/复制/连接池/密码策略；脚本有，真机没跑过 |
| 运维 | 生产部署本身 | systemd、TLS 反代、磁盘水位、跨机恢复 |
| 安全 | mTLS / 短期凭证 | scope 解决"能做什么"，不解决"凭证长期有效" |
| 安全 | 玩家 token 吊销 / `aud` | spec 0011 遗留：封号不能立即生效；token 也不区分客户端类型 |

## 6. 未归类缺口（2026-11-03 盘点发现，未进任何清单）

前三节是按里程碑排的。这一节是盘点时发现的、**从来没有被写进路线图**的东西——它们不是"以后再说"，
而是没人命名过，所以不会有人排期。按"谁解开它"同样分三层。

### 6.1 工程与流程（CI 里没有的门禁）

| 项 | 现状 | 代价 | 状态 |
|---|---|---|---|
| 依赖漏洞扫描 | 无 `govulncheck`、无 Dependabot/Renovate | 低（依赖少），但漏了只能在事故里发现 | ✅ `verify` job 跑 `govulncheck`（可达漏洞 = 构建失败） |
| 静态检查层 | 只有 `gofmt` + `go vet` | 中 | ✅ `staticcheck`（版本钉住）进 `verify` job 与 `scripts/verify.*` |
| 覆盖率 | CI 不输出、无阈值 | 中 | ✅ `scripts/coverage-check.sh`，不含 `tools/` 的地板 58%（当前 60.5%） |
| **文档门禁** | 链接检查曾是 `docs/README.md` 里的手工命令；`roadmap.md ↔ .html` 靠人同步 | 已发生 5 次计数不一致（本次盘点修的就是） | ✅ `scripts/docs-check.sh` + `verify` job |
| 发布说明 | 镜像按 `<sha>` 推，无 CHANGELOG/release notes | 回滚靠人记 | ⬜ 以后 |
| Makefile | 15 个 target，CI 一个都没用；Windows 没有 `make` | 低，但是双份真相 | ⬜ 以后 |

### 6.2 运维（比 §1.1 更细）

| 项 | 现状 | 状态 |
|---|---|---|
| **告警送不到人** | 规则会触发，但 `deploy/prometheus/` 只有抓取配置与规则，没有 Alertmanager：没有路由、去重、静默、接收人 | ✅ `alertmanager.yml` + prod compose 的 `observability` profile + `ops` job 用 `amtool check-config` 校验 |
| 归档只做了一半 | 只搬 `finished` 且已确认释放的会话；`failed` 会话永久堆在源表；也没有"搬回来"的脚本 | ✅ `failed` 会话纳入（不待回收者）、`scripts/db-archive-restore.sh`、`ops` job 断言双向 |
| 30 天窗口 vs 15 天保留 | SLO 要 30 天窗口，Prometheus `retention=15d` | ⬜ 提高保留或加远端写入 |
| 日志聚合与 tracing | 指标之外没有任何横切观测 | ⬜ 有 k8s/托管日志时再上 |
| 镜像与备份的保留策略 | 未定（`deploy.md` §11.7 自己列为"没有 CI 覆盖"） | ⬜ 部署选择 |
| 告警抑制/静默策略 | Alertmanager 配置里 `inhibit_rules` 是空的，注释写清了原因（没有发布标记可依据） | ⬜ 有发布钩子后再加 |

### 6.3 产品与领域（代码里有痕迹，没人写规格）

| 项 | 现状（核实过） | 需要谁 |
|---|---|---|
| **队伍排队只做了一半** | `CreateTicketRequest.Party` 会存进队列表，但 `store.Pop` 的配对逻辑完全不看 party——同一队伍可能被拆到不同对局 | 产品拍板：party 参与配对，还是契约里明确"仅记录" |
| **economy 没有价目表** | `purchase` 的 `amount` 由调用方传，注释写"the server owns pricing"，但代码里没有价格来源 | 产品拍板：定价权归调用方还是要有目录/价目 |
| 排行榜写死 50 条 | `rank.get_leaderboard` 里 `limit := 50`，无查询参数、无周期/赛季（刚给 ledger 做完游标分页，这里反而更差） | 领域设计 |
| 无商店/物品目录、无成就/任务、无 MMR 衰减 | 只有 `economy.grant`/`purchase`/`wallet`/`ledger` | 产品 |
| 无好友/邀请/私聊 | team 服务自己实现了 create/join/get，Nakama 的社交能力没接 | 产品 |

> 这一节的作用：让"没人命名过的缺口"变成有人命名的。它们不该挤进 M2–M5 的里程碑，
> 但也不该在下一次盘点时才被发现。

## 7. 怎么更新这页

1. 状态变化先改这里（Markdown）；同时改对应 spec 的「状态」行与 `docs/architecture-map.md` 的表格。
2. 然后同步 `docs/roadmap.html`（结构与本节一致）。
3. 关闭一项时：从"未实现/现在该做"移到 §5，并写清规格编号——没写规格的"完成"不算完成。
